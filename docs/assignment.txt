REST API резервирования товаров
Разработайте API небольшого склада. Пользователь резервирует нужное количество одного товара на 10 минут, затем подтверждает или отменяет резерв. Если срок истёк, система освобождает товар. При одновременных запросах нельзя зарезервировать больше единиц, чем есть на складе.
Формат и объём
Ориентир — 8–12 часов. Укажите фактическое время. Если достигли лимита, сдайте работающую часть и перечислите незавершённое. Архитектуру и схему хранения выберите самостоятельно. После сдачи предполагается обсуждение решения в течение 45–60 минут.
Стек: поддерживаемая стабильная версия Laravel, совместимая версия PHP, PostgreSQL, Redis, Docker Compose. Зафиксируйте версии и зависимости. Подготовьте сидер с двумя пользователями, тестовыми токенами и несколькими товарами. Регистрация и административный интерфейс в объём не входят.
Правила резервирования
•	Один резерв содержит один product_id и целое quantity > 0. Новый резерв получает состояние reserved и серверный expires_at через 10 минут. Продление срока не предусмотрено.
•	Создание удерживает количество. Подтверждение превращает удержание в окончательный расход; свободный остаток повторно не уменьшается. Отмена и истечение возвращают количество ровно один раз.
•	Исходный запас равен сумме свободного количества, ещё удерживаемого количества и подтверждённого расхода. Все величины неотрицательны. Пополнений и возвратов покупок в проекте нет.
•	При серверном времени t >= expires_at первый переход в confirmed или cancelled запрещён, даже если очередь задержалась. Время проверяется при атомарном принятии решения, после ожидания блокировок; время клиента не используется.
Состояние	Подтверждение	Отмена
reserved, срок не истёк	confirmed, HTTP 200	cancelled, HTTP 200
reserved, срок истёк	HTTP 409	HTTP 409
confirmed	HTTP 200, без изменений	HTTP 409
cancelled	HTTP 409	HTTP 200, без изменений
expired	HTTP 409	HTTP 409

Состояния confirmed, cancelled, expired окончательные. Повтор уже выполненного действия возвращает HTTP 200 и после дедлайна. Фоновое истечение переводит только просроченный reserved в expired.
Контракт API
Все маршруты имеют префикс /api/v1 и используют JSON. Доступ по Bearer-токену; достаточно Laravel Sanctum или другого обоснованного механизма. Пользователь читает и изменяет только собственные резервы. Для чужого и отсутствующего резерва возвращайте одинаковый HTTP 404.
Метод и маршрут	Поведение
GET /products	Каталог с пагинацией и доступным количеством. Ограничьте максимальный размер страницы.
GET /products/{id}	Карточка товара и доступное количество.
POST /reservations	Создание резерва. Обязателен заголовок Idempotency-Key.
GET /reservations/{id}	Текущее сохранённое состояние собственного резерва.
POST /reservations/{id}/confirm	Подтверждение по правилам переходов.
POST /reservations/{id}/cancel	Отмена по правилам переходов.

Пример создания
POST /api/v1/reservations
Authorization: Bearer <token>
Idempotency-Key: reserve-demo-001
Content-Type: application/json

{"product_id": 1, "quantity": 2}
Первое успешное создание возвращает HTTP 201. Представление резерва содержит как минимум id, product_id, quantity, status, created_at, expires_at. Даты передавайте в ISO 8601 с часовым поясом; для проекта используйте UTC. Остальную структуру JSON выберите и опишите в README.
Валидация и ошибки
HTTP	Когда возвращать
401	Нет действительного токена.
404	Товар или доступный пользователю резерв не найден.
409	Недостаточно товара, недопустимый переход состояния или конфликт идемпотентности.
422	Невалидные поля, quantity не является положительным целым, отсутствует или невалиден Idempotency-Key.

Для ошибок используйте стабильный машинный code и понятный message; ошибки полей могут включать details. Различайте причины HTTP 409, например insufficient_stock, reservation_expired, idempotency_conflict. Владелец, статус и срок резерва определяются сервером и не могут задаваться клиентом.
Идемпотентность и согласованность данных
Повтор создания резерва
Idempotency-Key — непустая строка длиной до 128 символов. Область ключа — один пользователь и операция создания резерва. Разные пользователи могут использовать одинаковую строку независимо.
•	После успешного создания повтор с тем же ключом, product_id и quantity возвращает HTTP 200 и тот же резерв в его текущем сохранённом состоянии. Дополнительного удержания нет; expires_at не продлевается.
•	Правило действует и после подтверждения, отмены или истечения резерва. Для нового резерва нужен новый ключ.
•	Уже использованный ключ с другим product_id или quantity возвращает HTTP 409 с кодом idempotency_conflict. Сравнивайте значения полей после валидации, а не форматирование JSON.
•	Одновременные одинаковые запросы создают ровно один резерв при достаточном остатке. Можно дождаться результата первой операции либо вернуть HTTP 409 с кодом request_in_progress; после её завершения повтор должен вернуть существующий резерв.
•	Ошибки валидации, доступа и нехватки остатка ключ не закрепляют. Ключ закрепляется атомарно с успешным созданием. Для тестового проекта храните успешные ключи вместе с историей резервов без очистки.
Требования к PostgreSQL
PostgreSQL является источником истины для резервов и количества товара. Способ обеспечения согласованности выберите самостоятельно и объясните. Решение должно работать при нескольких процессах API и нескольких worker.
•	Конкурентные запросы с разными ключами не могут удержать больше доступного количества. Решение о создании нельзя принимать по кешированному остатку.
•	Подтверждение, отмена и истечение одного резерва должны конкурировать безопасно. Допустим ровно один окончательный переход и соответствующее ему изменение количества.
•	Предусмотрите транзакционные границы, необходимые ограничения данных и индексы. Согласованность должна сохраняться при откате; успешный резерв не должен оставаться без закреплённого ключа.
•	Схема таблиц, способ блокировок, обработка конфликтов и расположение бизнес-логики — часть вашего решения. Покажите, какие инварианты обеспечиваются базой, а какие — кодом приложения.
Пример: при исходном запасе 5 резерв на 3 оставляет 2 свободные единицы. Подтверждение сохраняет 2 свободные единицы и фиксирует расход 3. Отмена такого неподтверждённого резерва возвращает свободное количество к 5.
Пример повторного создания резерва. Один пользователь отправляет два одинаковых запроса с ключом reserve-demo-001: {"product_id":1,"quantity":2}. Дата — 15 ноября 2026, время UTC. Показана часть полей ответа.
Запрос	HTTP	id	expires_at
Первый в 10:00:00	201	123	2026-11-15T10:10:00Z
Повтор в 10:03:00	200	123	2026-11-15T10:13:00Z

Redis и проверка поведения
Кеш и очередь
•	Используйте Redis для кеширования каталога или карточки товара с TTL 30 секунд. Отображаемый остаток справочный и может отставать в пределах TTL. Инвалидация допустима, но немедленная актуализация кеша не обязательна; при создании проверяйте достоверный остаток в PostgreSQL.
•	Используйте Redis как backend очереди для фонового истечения резервов. Способ планирования выберите самостоятельно. Повторная доставка задания и несколько worker не должны повторно возвращать количество или менять окончательное состояние.
•	В исправном окружении обработка просроченных резервов запускается не реже раза в минуту. Допустимая задержка освобождения — интервал запуска плюс время обработки; жёсткое нагрузочное SLA не требуется.
•	До фоновой обработки просроченный резерв может сохранять статус reserved и удерживать товар. Это не разрешает его подтверждать или отменять. Преждевременное задание не должно освобождать действующий резерв.
•	Добавьте способ повторно найти просроченные резервы в PostgreSQL и запустить их обработку: Artisan-команду или периодический проход. Он нужен для восстановления пропущенных заданий и должен быть безопасен при повторе.
В README опишите поведение при остановленном worker, недоступном Redis и сбое между фиксацией данных и отправкой задания. Допустим контролируемый отказ операции или продолжение с восстановлением, если сохраняются инварианты. Реализация outbox и отказоустойчивого кластера не требуется.
Обязательные проверки
Используйте PHPUnit или Pest. Интеграционные проверки состояния и конкуренции выполняйте на PostgreSQL. Проверяйте итоговые записи и количество товара, а не только HTTP-коды.
•	Создание, нехватка остатка, подтверждение, отмена и истечение; невалидные количества и чужой резерв.
•	Повтор ключа с тем же и другим телом; повтор после перехода в окончательное состояние; одинаковый ключ у разных пользователей.
•	Повторные confirm, cancel и job; старое задание после подтверждения; задание до дедлайна; отказ первого подтверждения при наступлении expires_at до обработки очереди.
•	Восстановление пропущенного истечения через предусмотренную команду или периодический проход.
Приложите один небольшой тестовый инструмент с двумя реально параллельными сценариями: 20 запросов на последнюю единицу с разными ключами и 20 одинаковых запросов с одним ключом. Подойдут интеграционный тест или скрипт. При необходимости повторите ответы request_in_progress до завершения. Поясните, как обеспечивается параллельность; последовательный цикл не считается такой проверкой.
Гонки confirm/cancel и confirm/expire разберите в README и будьте готовы показать в коде. Их отдельный параллельный тест полезен, но не обязателен. Для тестов времени используйте управляемые часы или сокращаемый TTL, чтобы не ждать 10 минут.
Сдача работы и критерии оценки
Передайте Git-репозиторий или архив с исходниками, миграциями, сидерами, тестами, Docker Compose и .env.example. Секреты в репозиторий не добавляйте. Окружение должно позволять запустить API, PostgreSQL, Redis, worker и нужный планировщик по инструкции без ручного редактирования кода.
Что включить в README
•	Команды запуска, миграций, заполнения данных и получения тестовых токенов; команды запуска тестов и двух конкурентных сценариев.
•	Примеры запросов и ответов, коды ошибок, формат пагинации и допустимые входные значения. Достаточно README с curl; отдельная OpenAPI-спецификация необязательна.
•	Краткое описание модели данных, транзакционных границ, защиты остатка и конкурентных повторов ключа.
•	Как устроены кеширование, время жизни резерва, повтор jobs и восстановление пропущенного истечения; что происходит при сбоях Redis и worker.
Границы задания
Не требуется разрабатывать фронтенд, регистрацию, CRUD товаров, корзину, несколько позиций в резерве, платежи, уведомления, роли администратора, микросервисы, CI/CD или мониторинг. DDD, CQRS, Repository Pattern, Horizon и другие инструменты используйте только при необходимости. Дополнительные функции сами по себе баллов при оценке решения не дают.
Можно использовать документацию, библиотеки и AI-инструменты. Кратко укажите существенную помощь в README и будьте готовы объяснить и изменить любую часть решения на обсуждении.
