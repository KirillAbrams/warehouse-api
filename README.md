# Служба резервирования товаров

Приложение позволяет посмотреть товары, отложить нужное количество на десять минут, подтвердить резерв или отменить его. Если срок закончился, приложение возвращает товар в свободный остаток.

Проект написан на Laravel. PostgreSQL хранит товары, пользователей и резервы. Redis хранит очередь заданий и временную копию каталога для быстрого чтения. Работа идёт через запросы к приложению. Отдельных страниц магазина и входа по паролю здесь нет.

Исходники проекта: [KirillAbrams/warehouse-api](https://github.com/KirillAbrams/warehouse-api).

В этом файле описаны запуск, запросы, правила работы, проверки и назначение файлов. Исходное задание сохранено в `docs/assignment.txt`.

Названия файлов, команд и полей оставлены как в проекте, чтобы их можно было найти и скопировать. Пояснения написаны по-русски. Английские названия внутри команд являются их обязательной частью.

## Что нужно для запуска

Установите и запустите Docker с поддержкой Docker Compose. На компьютере не нужно отдельно устанавливать PHP, Composer или PostgreSQL. Для первой сборки нужен доступ к сети, чтобы получить образы и библиотеки.

Распакуйте архив, откройте папку проекта в терминале и выполните:

```sh
./bin/setup
```

Команда сама выполнит подготовку:

1. Создаст `.env` из `.env.example`, если своего файла настроек ещё нет.
2. Подготовит сеть проекта. Если стандартные диапазоны Docker закончились, сама найдёт свободный частный диапазон.
3. Соберёт среду выполнения и установит библиотеки по версиям из `composer.lock`.
4. Создаст ключ приложения, если он ещё не задан.
5. Запустит PostgreSQL и Redis, создаст таблицы и учебные записи.
6. Запустит приложение, приём запросов, обработку очереди и расписание.
7. Выведет два ключа доступа для учебных пользователей.

После запуска приложение отвечает по адресу `http://localhost:8187`. По этому адресу виден короткий ответ с названием службы. Сами товары и резервы доступны по адресам из раздела «Запросы к приложению».

Проверить состояние служб:

```sh
docker compose ps
```

Если у вас установлена отдельная команда `docker-compose`, замените ею `docker compose` в примерах. Команды `bin/setup` и `bin/check` выбирают доступный вариант сами.

Повторный запуск `bin/setup` сохраняет существующие остатки и историю резервов. При этом учебные ключи доступа заменяются новыми. Старые учебные ключи перестают работать.

## Сеть Docker готовится автоматически

Для первого запуска по-прежнему достаточно `./bin/setup`. Отдельно создавать сеть и менять настройки Docker не нужно.

Подготовка получает имя текущего проекта из Compose и проверяет его сеть. Если сеть уже существует и принадлежит этому проекту, она используется повторно. Если сети ещё нет, команда сначала пробует обычное создание. Когда стандартный запас адресов исчерпан, она перебирает небольшие частные диапазоны. Занятые диапазоны пропускаются.

Команда проверяет не больше 64 частных диапазонов. Она не удаляет сети, не останавливает другие проекты и не меняет общие настройки Docker. Сеть с совпавшим именем, но другим владельцем вызывает понятный отказ. Ошибки подключения к Docker также не скрываются.

Для второй независимой копии приложения задайте другое имя через `COMPOSE_PROJECT_NAME` и другой порт в `.env`. Например, имя `warehouse-second`, порт `8188` и адрес `http://localhost:8188`. Тогда у копии будут свои сеть, контейнеры и хранилища. Обычно эти настройки менять не требуется.

## Настройки и учебные данные

Настройки находятся в `.env`. Этот файл создаётся при подготовке и не входит в архив. Образец настроек находится в `.env.example`.

| Настройка | Для чего нужна |
| --- | --- |
| `APP_KEY` | Внутренний ключ приложения. Создаётся при подготовке |
| `APP_URL` | Адрес приложения. По умолчанию `http://localhost:8187` |
| `API_PORT` | Местный порт приёма запросов. По умолчанию `8187` |
| `DB_DATABASE` | Основная база с учебными данными. По умолчанию `warehouse` |
| `DB_USERNAME`, `DB_PASSWORD` | Имя и пароль доступа к местной базе |
| `REDIS_DB` | Номер хранилища очереди. По умолчанию `0` |
| `REDIS_CACHE_DB` | Номер хранилища временного каталога. По умолчанию `1` |
| `REDIS_PREFIX` | Начало имён записей приложения в Redis |
| `RESERVATION_TTL_SECONDS` | Срок нового резерва в секундах. По умолчанию `600` |

Пароль в образце предназначен для местного учебного запуска. Приложение открывает порт только на этом компьютере. Порты базы, Redis и выполнения PHP наружу не опубликованы.

Если порт `8187` занят, измените `API_PORT` и адрес в `APP_URL`, затем повторите `./bin/setup`. После изменения срока уже созданные резервы сохраняют первоначальную дату окончания.

При первом заполнении появляются пользователи `alice@example.test` и `bob@example.test`. Для них создаются случайные ключи доступа. Пароли также случайные, но вход по паролю не предусмотрен.

| Артикул | Товар | Начальное количество |
| --- | --- | --- |
| `KB-001` | Клавиатура | 5 |
| `MS-001` | Мышь | 12 |
| `MN-001` | Монитор | 3 |

Названия этих товаров в ответах приложения записаны по-английски. При повторном заполнении базы существующие товары не создаются заново, а их количество не сбрасывается.

Получить новые учебные ключи без повторной подготовки:

```sh
docker compose exec -T app php artisan demo:tokens
```

Команда заменяет только ключи с именем `demo` у двух учебных пользователей. Остальные ключи не затрагиваются. Замена выполняется целиком: ошибка не оставляет одного пользователя с новым ключом, а другого со старым. Если учебного пользователя нет, команда попросит заполнить базу:

```sh
docker compose exec -T app php artisan db:seed --force
```

## Запросы к приложению

Все адреса ниже требуют ключ доступа. Добавляйте заголовок `Authorization: Bearer ВАШ_КЛЮЧ`, заменив `ВАШ_КЛЮЧ` значением из команды получения ключей. Ключ определяет пользователя и владельца резерва.

В примерах также передаётся `Accept: application/json`. Ответы имеют вид JSON, то есть содержат именованные поля и значения. При создании резерва нужен заголовок `Content-Type: application/json`.

| Способ запроса | Адрес | Действие |
| --- | --- | --- |
| `GET` | `/api/v1/products` | Получить страницу каталога |
| `GET` | `/api/v1/products/{id}` | Получить один товар |
| `POST` | `/api/v1/reservations` | Создать резерв |
| `GET` | `/api/v1/reservations/{id}` | Посмотреть свой резерв |
| `POST` | `/api/v1/reservations/{id}/confirm` | Подтвердить свой резерв |
| `POST` | `/api/v1/reservations/{id}/cancel` | Отменить свой резерв |

Вместо `{id}` указывается номер товара или резерва. Номер товара берётся из каталога, номер резерва из ответа на создание. Чужой резерв выглядит так же, как отсутствующий: приложение возвращает `404`.

### Посмотреть товары

```sh
curl -sS 'http://localhost:8187/api/v1/products?per_page=2&page=1' \
  -H 'Accept: application/json' \
  -H 'Authorization: Bearer ВАШ_КЛЮЧ'
```

В ответе `data` содержит товары, `links` содержит ссылки на страницы, `meta` содержит номер страницы и общее количество. У товара есть поля `id`, `sku`, `name`, `available_quantity`: номер, артикул, название и свободное количество.

Параметр `page` задаёт страницу, начиная с `1`. Параметр `per_page` задаёт количество товаров на странице от `1` до `100`, по умолчанию `20`. Товары всегда упорядочены по номеру. За последней страницей возвращается пустой список.

Каталог может показывать количество с задержкой до 30 секунд. При создании резерва приложение заново проверяет основную базу. Если копия каталога в Redis недоступна, чтение продолжается из PostgreSQL.

### Создать резерв

В примере используется товар с номером `1`. Сначала убедитесь, что такой товар есть в каталоге и доступно нужное количество.

```sh
curl -sS -X POST http://localhost:8187/api/v1/reservations \
  -H 'Accept: application/json' \
  -H 'Authorization: Bearer ВАШ_КЛЮЧ' \
  -H 'Content-Type: application/json' \
  -H 'Idempotency-Key: reserve-demo-001' \
  -d '{"product_id":1,"quantity":2}'
```

`product_id` задаёт номер товара. `quantity` задаёт положительное целое количество. Количество передаётся числом, а не строкой: значение `2` допустимо, значение `"2"` отклоняется. Номер товара допускается целым числом или строкой с целым числом. Дробные и логические значения не подходят.

Заголовок `Idempotency-Key` защищает от случайного повторного удержания товара, например после потери ответа. Для нового намерения создать резерв используйте новый ключ. Для повтора того же запроса оставляйте прежний ключ.

Ключ должен содержать хотя бы один непробельный знак, не содержать управляющих знаков и быть не длиннее 128 знаков. Приложение хранит его отдельно для каждого пользователя. Ключ из тела запроса не подменяет обязательный заголовок.

При первом успешном создании приложение возвращает `201`, при повторе того же запроса с тем же ключом `200`. Повтор возвращает тот же резерв, не удерживает товар ещё раз и не продлевает срок. Тот же ключ с другим товаром или количеством возвращает `409`. Неуспешная попытка создания не занимает ключ.

Владелец, состояние и даты назначаются приложением. Поля `user_id`, `owner_id`, `status`, `expires_at`, `created_at`, `updated_at`, `finalized_at`, `id` не нужно передавать. Их присутствие отклоняется, даже если значение пустое.

В `data` ответа на создание находятся:

| Поле | Значение |
| --- | --- |
| `id` | Номер резерва |
| `product_id` | Номер товара |
| `quantity` | Удержанное количество |
| `status` | Текущее состояние резерва |
| `created_at` | Время создания |
| `expires_at` | Время окончания срока |

Даты записаны в UTC с точностью до микросекунд. Буква `Z` в конце даты указывает на этот часовой пояс.

### Посмотреть, подтвердить или отменить резерв

Замените `123` в примерах номером созданного резерва.

Посмотреть:

```sh
curl -sS http://localhost:8187/api/v1/reservations/123 \
  -H 'Accept: application/json' \
  -H 'Authorization: Bearer ВАШ_КЛЮЧ'
```

Подтвердить:

```sh
curl -sS -X POST http://localhost:8187/api/v1/reservations/123/confirm \
  -H 'Accept: application/json' \
  -H 'Authorization: Bearer ВАШ_КЛЮЧ'
```

Отменить:

```sh
curl -sS -X POST http://localhost:8187/api/v1/reservations/123/cancel \
  -H 'Accept: application/json' \
  -H 'Authorization: Bearer ВАШ_КЛЮЧ'
```

Подтверждение и отмена не требуют тела запроса и нового ключа повтора. Успешное действие возвращает `200` и данные резерва.

## Состояния, сроки и остатки

| Значение `status` | Смысл |
| --- | --- |
| `reserved` | Товар удерживается до окончания срока |
| `confirmed` | Резерв подтверждён, товар больше не свободен |
| `cancelled` | Резерв отменён, товар возвращён в свободный остаток |
| `expired` | Срок закончился, товар возвращён в свободный остаток |

Подтвердить или отменить впервые можно только действующий резерв до окончания срока. Ровно в момент `expires_at` срок уже закончился. Первый запрос подтверждения или отмены после этого момента получает `409`.

Повтор уже выполненного действия возвращает `200`, в том числе после первоначального срока. Подтвердить отменённый резерв, отменить подтверждённый или изменить просроченный нельзя. Такие запросы получают `409`.

Чтение резерва само по себе его не меняет. Если обработчик очереди задержался, чтение может ещё показать `reserved` с прошедшей датой. Это не позволяет подтвердить просроченный резерв: изменение состояния отдельно проверяет текущее время базы.

Для товара всегда сохраняется равенство: начальное количество равно сумме свободного, удержанного и подтверждённого количества. Создание переносит количество из свободного в удержанное. Подтверждение переносит удержанное в подтверждённое. Отмена и истечение возвращают удержанное в свободное. Повтор действия не меняет эти числа ещё раз.

Чтобы два запроса не забрали последнюю единицу одновременно, приложение ждёт освобождения нужных записей в PostgreSQL. Изменение резерва сначала удерживает его запись, затем запись товара и только после этого читает время. Создание сначала согласует одинаковые ключи пользователя. Все связанные изменения сохраняются вместе либо целиком отменяются при ошибке.

### Что означают номера ошибок

| Номер | Причина |
| --- | --- |
| `401` | Ключ доступа отсутствует или недействителен |
| `404` | Товара нет, резерва нет или он принадлежит другому пользователю |
| `409` | Не хватает товара, ключ уже использован с другими данными или состояние не допускает действие |
| `422` | Неверные поля, количество, номер страницы или обязательный заголовок |

Ошибка содержит поле `error` с причиной и сообщением. Ошибка проверки полей также содержит подробности по полям. Постоянные значения причин позволяют вызывающей программе различать ошибки без разбора текста сообщения.

## Как освобождаются просроченные резервы

Служба `scheduler` каждую минуту запускает поиск резервов с закончившимся сроком. Команда ставит задания в очередь `reservations`, а служба `worker` выполняет их.

Повторный поиск пропускает задания, которые уже ждут, выполняются или ожидают новой попытки. Несколько одновременных запусков команды согласуются через PostgreSQL, чтобы не заполнять очередь копиями. Задание хранит номер резерва. Перед изменением приложение снова читает резерв и проверяет срок.

Если сообщение потеряно или окончательно завершилось с ошибкой, следующий поиск сможет поставить его снова. Повторное выполнение не возвращает одно количество товара несколько раз. Если очередь остановлена, обычный поиск не заменяет её самостоятельной обработкой.

Запустить поиск вручную:

```sh
docker compose exec -T app php artisan reservations:expire
```

Освободить просроченные резервы прямо в текущем процессе, без очереди:

```sh
docker compose exec -T app php artisan reservations:expire --sync
```

Посмотреть сообщения обработчика и расписания:

```sh
docker compose logs --tail=100 worker scheduler
```

Посмотреть задания, исчерпавшие попытки:

```sh
docker compose exec -T app php artisan queue:failed
```

У задания три попытки и ограничение выполнения 30 секунд. Очередь считает зависшее задание доступным для повторного получения через 90 секунд. Паузы перед новыми попытками заданы в `app/Jobs/ExpireReservationJob.php`.

## Проверки проекта

Основная команда:

```sh
./bin/check
```

Она проверяет оформление кода через Pint, типы через Larastan на уровне 8 и запускает весь набор проверок поведения через PHPUnit.

Для проверок используется отдельная база `warehouse_test`. Она создаётся при первой подготовке хранилища PostgreSQL. Общая основа проверок отказывается работать с другой базой. В Redis используются имена с отдельным началом `warehouse_test_`. Не запускайте одновременно два набора проверок на этой же базе.

Последний полный прогон: **141 проверка, 3202 проверенных условий**. Проверки охватывают запросы, владельцев, остатки, повторные действия, сроки, очередь, временный каталог и одновременную работу нескольких процессов.

Проверки подготовки запускают настоящую команду оболочки с управляемыми ответами Docker. Они проверяют также ошибки, повторное создание и ограничение числа попыток. К настоящим сетям компьютера эти проверки не обращаются.

Проверки времени подставляют управляемые часы. Проверки ожидания записи в базе запускают отдельный процесс и действительно ждут блокировку. Для проверки остатков выполняются 96 последовательностей действий с фиксированным исходным числом `20261115`, чтобы результат можно было повторить.

Покрытие измеряется на всей папке `app/`: 307 из 307 исполняемых строк и 93 из 93 ветвей. По обоим показателям 100%. Код из отчёта не исключён. Покрытие показывает, какие части были выполнены проверками. Само по себе оно не гарантирует отсутствие ошибок.

Повторить измерение:

```sh
docker compose exec -T -e XDEBUG_MODE=coverage app php -d memory_limit=1G \
  vendor/bin/phpunit --path-coverage \
  --coverage-clover storage/framework/testing/clover.xml \
  --coverage-php storage/framework/testing/coverage.php
```

Отчёты появятся в `storage/framework/testing`. Комментарии в исходниках написаны на английском. Этот документ написан на русском.

### Дополнительная проверка одновременных запросов

```sh
docker compose exec -T app php tools/concurrency.php
```

Эта команда обращается к работающему приложению через веб-сервер. В каждом из двух случаев она удерживает товар в базе, собирает 20 действительно ожидающих запросов, затем разрешает им продолжить работу.

При разных ключах только один запрос получает последнюю единицу товара: один ответ `201`, остальные `409`. При одинаковом ключе создаётся один резерв: один ответ `201`, остальные `200`. После ответов команда отдельно проверяет записи и все счётчики товара в базе.

Эта команда добавляет собственные помеченные товары, пользователя и резервы в основную учебную базу. История остаётся для просмотра. Команда не включена в `bin/check`.

## Остановка и повторный запуск

Остановить службы с сохранением данных:

```sh
docker compose stop
```

Запустить уже подготовленные службы:

```sh
docker compose up -d --wait
```

Удаление хранилищ Docker удаляет и данные. Для обычной остановки это не требуется. Подробности ошибки приложения можно посмотреть через `docker compose logs --tail=100 app`.

## Как устроен код

Расположение классов приведено к образцу [umbrellax-laravel](https://github.com/phosphoriat/umbrellax-laravel/tree/9884ce22f40ef3105d70705b0a627dd3b3306418). Для сравнения использована эта закреплённая версия.

Контроллеры лежат непосредственно в `app/Http/Controllers`. Они получают запрос, передают проверенные поля сервису и возвращают ответ. Проверки полей сгруппированы по сущностям в `app/Http/Requests/Product` и `app/Http/Requests/Reservation`. Поля ответов описаны в `app/Http/Resources`.

Основные правила находятся в `app/Services`. `ReservationService` создаёт резерв, подтверждает или отменяет его и освобождает товар после окончания срока. `ProductService` читает товары и возвращает модели, с которыми работают классы ответа. Сохранённая временная копия каталога сохраняет прежний состав полей, поэтому читается и после обновления. `DemoTokenService` заменяет учебные ключи. `ReservationQueueService` находит уже поставленные задания, а `PostgresClock` получает фактическое время базы после ожидания записей.

`app/Contracts/ClockInterface.php` задаёт требование к часам. Рабочий запуск читает время PostgreSQL, а проверки могут подставить управляемое время. `app/Enums` хранит допустимые состояния. `app/Models` описывает записи и связи базы. Модель резерва выполняет подтверждение, отмену и освобождение товара после проверок сервиса. Эти действия остаются внутри общей операции базы с удержанием записей. `app/Jobs` содержит задание очереди. `app/Providers` подключает общие настройки приложения.

Папки `Actions`, `Queries`, `Support` и `Data` в приложении не используются. Адреса запросов по-прежнему начинаются с `/api/v1`. Перенос файлов не меняет формат запросов, ответов, состояния резервов или правила изменения остатков.

Время истечения, проверки владельца и изменения остатков остаются внутри прежних границ операций базы. Существующие сообщения очереди с именем `App\Jobs\ExpireReservation` читаются после переименования задания в `ExpireReservationJob`. Проверка совместимости использует сохранённое сообщение старой версии.

Команда `./bin/setup` создаёт только сеть и хранилища своего запуска. Собственный образ получает имя текущего проекта Docker. Это позволяет проверять копию рядом с другими приложениями без замены их образов. При занятом местном порте можно выполнить `API_PORT=8188 ./bin/setup`.

## Соглашения при изменении кода

Расположение файлов и основные приёмы приняты по указанному образцу. Оформление проверяется настройками в `pint.json`.

1. Адреса каждой версии находятся в своём файле. `RouteServiceProvider` подключает `routes/api/v1.php` с началом адреса `/api/v1`.
2. Стандартные действия подключаются через `apiResource`. Подтверждение и отмена собраны в группе контроллера резервов. Новые неподдерживаемые действия автоматически не открываются.
3. Контроллер получает модель, проверяет право действия и возвращает ответ. Правила владельца находятся в `ReservationPolicy`. Сервис повторно проверяет владельца при удержании записи базы.
4. Основные сервисы вызываются по имени класса. Часы реализуют общий интерфейс и получают соединение базы через Laravel, чтобы проверки могли управлять временем.
5. В модели сначала идут подключения и настройки полей, затем связи и действия. Изменение остатков выполняется методами модели после проверок сервиса внутри той же операции базы.
6. Класс ответа читает поля модели напрямую. Проверка параметров списка называется `FilterRequest`.
7. Комментарии в исходниках пишутся на английском. Перед методом контроллера указываются действие, способ запроса и адрес. Комментарии к ожиданию записей объясняют порядок действий и причину выбора времени.
8. Перед передачей изменений выполняются `./bin/check` и измерение покрытия. Сохраняются ответы, остатки, правила повторов и срок уже созданных резервов.

## Подготовка проекта

При подготовке исходников, комментариев и проверок использовался помощник с искусственным интеллектом. Решения проверялись автоматическими тестами и отдельными запросами к работающему приложению. Общее время подготовки в несколько этапов не фиксировалось.
